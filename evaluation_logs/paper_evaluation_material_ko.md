# STM32 메모리 오류 탐지기 통합 평가 보고서

작성일: 2026-07-19
대상: STM32L562E-DK (Arm Cortex-M33), Juliet Dynamic CWE

## 1. 핵심 결과

| 평가 축 | 최종 결과 | 논문에서의 해석 |
| --- | ---: | --- |
| 평가 대상 | 9개 CWE, 36개 그룹, 266개 테스트 | `rand` 및 고정 8 B 미만 침범 제외 |
| 제안 시스템 탐지 성공 | **250/266 (94.0%)** | bad 탐지, good 정상 완료 |
| full 미탐 | **16/266 (6.0%)** | 원인별 한계 분석 대상 |
| full good-path 오탐 | **0/266 (0.0%)** | 비-`rand` 평가 집합 기준 |
| 순수 실행시간, full/runtime-only | **3.281x** | strict 정상 경로 243개 기하평균 |

### 결과 대시보드

```text
제안 시스템 성공률   94.0%  ███████████████████░  250 / 266
bad-path 미탐률       6.0%  █░░░░░░░░░░░░░░░░░░   16 / 266
good-path 오탐률      0.0%  ░░░░░░░░░░░░░░░░░░░    0 / 266

```

주요 결론은 제안한 LLVM 기반 메모리 오류 탐지 시스템이 설계 범위 안의
비결정 입력을 제외한 테스트에서 94.0%의 탐지 성공률과 0%의 good-path
오탐률을 보였다는 것이다.
정상 실행에 대한 순수 계측 비용은 runtime-only 대비 3.281배, 완전한
native 대비 4.283배였다.

### 2.3 테스트 제외 기준

다음 항목은 탐지 성능의 주 결과에서 제외했다.

| 제외 항목 | 제외 이유 |
| --- | --- |
| 이름에 `rand`가 포함된 테스트 | 난숫값에 따라 취약 전제조건과 bad/good 의미가 달라짐 |
| `CWE129` | 단일 4 B `int` 경계 초과로 탐지기의 8 B 단위보다 작음 |
| `CWE193` | 1 B `char` 또는 4 B `wchar_t` 종단문자 초과 |
| CWE122 s11의 `sizeof_double`, `sizeof_int64_t`, `sizeof_struct` | STM32의 4 B 포인터 크기로 인해 초과량이 4 B |

정확히 8 B를 침범하거나 침범량이 실행 상태에 따라 달라지는 테스트는
유지했다. 8 B 기준은 메모리 경계 오류에만 적용했으며 CWE191 산술 오류에는
적용하지 않았다. 이 필터를 적용한 최종 모집단은 266개다.

### 2.4 pass/fail 판정

| 상태 | bad 경로 | good 경로 | 의미 |
| --- | --- | --- | --- |
| `PASS` | 탐지 | 정상 완료 | 제안 시스템 성공 |
| `FAIL-MISS` | 미탐 | 정상 완료 | 취약 경로 미탐 |
| `FAIL-FP` | 탐지 | 탐지 | good-path 오탐 |
| `FAIL-BOTH` | 미탐 | 탐지 | 미탐과 오탐 동시 발생 |

제안 시스템의 탐지 성공률은 `PASS / 전체`, bad-path 탐지율은
`(PASS + FAIL-FP) / 전체`, good-path 오탐률은
`(FAIL-FP + FAIL-BOTH) / 전체`로 계산했다.

### 3.2 시스템 구성요소의 역할

본 프로젝트의 기여 단위는 LLVM 패스만이 아니라, 패스가 삽입한 검사를
수행하는 지원 런타임까지 포함한 **제안 시스템**이다. 지원 런타임은 태그
관리, heap 객체 추적, API wrapper, MPU 설정, 오류 보고와 복구를 담당하며
패스와 함께 탐지 동작을 완성한다. 따라서 위 250/266은 제안 시스템의 탐지
성공으로 해석한다.

| 구성요소 | 역할 | 결과 해석 |
| --- | --- | --- |
| LLVM 계측 패스 | load/store, 정수 연산, NULL 접근, MPU redzone 설정 지점 삽입 | software-tag, integer, null, mpu 탐지의 정적 계측 부분 |
| 지원 런타임 | 태그 비교, heap/free 상태 관리, API wrapper, MPU 적용, fault 복구 | 본 프로젝트의 런타임 기여이며 탐지 성공에 포함 |
| runtime-only 모드 | LLVM 계측 없이 지원 런타임과 API wrapper만 사용 | 구성요소 ablation 및 LLVM 계측 추가 비용 비교용 |
| native 모드 | 원본 코드와 기본 라이브러리만 사용 | 전체 시스템 비용 비교용 기준 |

다만 일반 CPU fault처럼 프로젝트가 설정한 검사 지점 없이 발생한 종료는
탐지 성공으로 과대 해석하지 않는다. 보고서의 주 결과는 “제안 시스템의
탐지 성공률”이며, runtime-only와 native 비교는 성공률을 깎기 위한 기준이
아니라 구성요소 역할과 비용을 설명하기 위한 보조 분석이다.

## 4. 순수 실행시간 Bench

### 4.1 측정 구간

```text
측정 밖                      DWT 측정 구간                   측정 밖
초기화 · setjmp · canary  →  start → good() → end  →  통계 · UART 출력
MPU/heap/tag reset                                         fault 복구
```

UART 출력, fault handler 처리, `longjmp`, `reset_mpu`, `heap_reset`,
`tags_reset`, stack canary 처리는 측정 구간에 포함하지 않았다. 따라서 아래
cycle 비율은 정상 `good()` 경로의 순수 실행시간 오버헤드다.

### 4.2 데이터 완전성

| Bench 분류 | 테스트 수 | 전체 대비 | 사용 방식 |
| --- | ---: | ---: | --- |
| strict 정상 반복 | **243** | **91.4%** | 주 실행시간 결과 |
| 결과는 있으나 반복 중 fault 존재 | 16 | 6.0% | 민감도 분석에만 포함 |
| full 결과 미도달 | 7 | 2.6% | 시간 집계에서 제외 |
| 평가 모집단 | **266** | **100.0%** | pass/fail과 동일한 필터 |

strict 집합은 full/runtime-only/native 세 모드 모두 유효한 median cycle을
갖고 full의 200회 반복에서 fault가 한 번도 없었던 테스트다. strict 집합의
full 측정 변동계수는 모두 5% 미만이었으며, 최대 CV도 0.63%였다.

### 4.3 전체 오버헤드

| 집계 | 테스트 수 | Full / Runtime-only | Full / Native | 비고 |
| --- | ---: | ---: | ---: | --- |
| **주 결과: strict** | **243** | **3.281x** | **4.283x** | fault 없는 정상 반복 |
| 민감도 분석 | 259 | 3.261x | 4.269x | 성공 반복 median은 있으나 16개에 fault 이력 |

각 테스트의 median cycle 비율을 구한 뒤 테스트 간 기하평균을 사용했다.
strict 집합의 Full/Runtime-only 비율 중앙값은 2.557배, 95백분위는
11.430배였다. 짧은 테스트는 고정적인 검사 호출 비용의 비중이 커서 비율의
상단 꼬리가 길게 나타났다.

### 5.1 정적 메모리

| CWE | 펌웨어 쌍 | Flash full | Flash runtime | Flash 증가율 | RAM full | RAM runtime |

| CWE122 | 8 | 226,346 B | 218,880 B | 3.41% | 36,968 B | 36,976 B |
| CWE124 | 4 | 226,840 B | 218,694 B | 3.72% | 36,968 B | 36,976 B |
| CWE126 | 3 | 228,043 B | 219,085 B | 4.09% | 36,968 B | 36,976 B |
| CWE127 | 4 | 226,994 B | 218,710 B | 3.79% | 36,968 B | 36,976 B |
| CWE191 | 5 | 225,754 B | 218,725 B | 3.21% | 36,968 B | 36,976 B |
| CWE415 | 1 | 224,032 B | 218,032 B | 2.75% | 36,968 B | 36,976 B |
| CWE416 | 1 | 225,952 B | 218,784 B | 3.28% | 36,968 B | 36,976 B |
| CWE476 | 1 | 224,360 B | 218,160 B | 2.84% | 36,968 B | 36,976 B |

full의 평균 Flash 증가는 8,091 B이며, CWE별 증가율은 2.75~4.27%다.
정적 RAM은 full이 8 B 작아 유의한 증가가 관찰되지 않았다. 이 비교는
공통 runtime을 포함한 runtime-only 대비 LLVM 계측 추가분이다.

### 5.2 정상 경로 동적 메모리

strict Bench 243개의 측정 구간 밖에서 수집한 high-water/peak 값은 다음과
같다.

| 지표 | Full | Runtime-only | Native | Full-Runtime |
| --- | ---: | ---: | ---: | ---: |
| 평균 stack high-water | 710.0 B | 534.0 B | 382.4 B | **+176.0 B** |
| stack 중앙값 | 524 B | 340 B | 160 B | **+184 B** |
| stack 최댓값 | 1,536 B | 1,536 B | 1,536 B | 0 B |
| 평균 heap peak | 111.9 B | 111.9 B | 추적 안 됨 | **0 B** |
| heap 최댓값 | 1,600 B | 1,600 B | 추적 안 됨 | **0 B** |

full과 runtime-only의 동적 heap 사용량은 같았고, LLVM 계측으로 인한 추가
heap 할당은 관찰되지 않았다. native에서는 allocator 추적 자체를 제거하므로
0 B 기록을 실제 heap 미사용으로 해석하지 않고 “추적 안 됨”으로 표기했다.

| 8 B 미만 침범 제외 | 작은 경계 오류 탐지 능력을 평가하지 않음 | 설계 한계와 제외 목록을 명시 |
| 구성요소 기여의 혼재 | LLVM 계측과 지원 런타임의 역할이 함께 관찰됨 | 주 결과는 제안 시스템 성공률로 보고하고, runtime-only/native는 ablation으로 제시 |
| 일반 CPU fault | 프로젝트 검사 없이 종료된 사례를 탐지 성공으로 과대 해석할 수 있음 | 프로젝트 검사 지점 또는 프로젝트 설정 MPU에서 발생한 오류만 탐지로 해석 |

| Bench fault 이력 16개 | 정상 실행 오버헤드에 오류 경로가 섞일 수 있음 | strict 주 결과에서 제외하고 민감도 분석만 제시 |
| microbenchmark 일반화 | Juliet의 짧은 good 경로가 실제 응용을 대표하지 않을 수 있음 | cycle 분포와 CWE별 결과를 함께 제시 |

## 8. 논문 본문용 요약

> STM32L562E-DK에서 9개 CWE의 Juliet Dynamic 테스트를 평가하였다.
> 비결정적 `rand` 테스트와 탐지기의 8바이트 granularity보다 작은 고정
> 침범을 제외한 266개 테스트에서 제안 시스템은 250개를 성공적으로
> 탐지하여 94.0%의 탐지 성공률을 보였다. 266개의 정상 경로에서는
> 오탐이 발생하지 않았다. CWE124, CWE127, CWE415, CWE416은 100%,
> CWE121과 CWE122는 각각 97.8%와 93.9%의 성공률을 기록했다.

> 정상 실행 비용은 UART 출력, fault handler, 복구 및 상태 초기화를 DWT
> 측정 구간 밖으로 분리해 측정하였다. 세 실행 모드가 모두 완료되고 200회
> 반복에서 fault가 없었던 243개 테스트에서, 테스트별 median cycle 비율의
> 기하평균은 full/runtime-only 3.281배, full/native 4.283배였다.
> 평균 Flash 증가는 runtime-only 대비 8,091바이트(3.70%)였고 정적 RAM
> 증가는 관찰되지 않았다. 정상 경로 stack high-water는 평균 176바이트
> 증가했으며 추가 동적 heap 할당은 관찰되지 않았다.

> 잔여 16개 미탐은 문자열 read sink 미계측 6개, 좁은 정수형의 승격 후
> 축소 4개, 하위 객체 경계 부재 5개, 취약 전제조건이 활성화되지 않은
> NULL 테스트 1개로 분류되었다. 본 결과의 기여 단위는 LLVM 계측 패스와
> 지원 런타임을 포함한 제안 시스템이며, runtime-only와 native 결과는
> 구성요소 역할과 비용을 분석하기 위한 보조 기준으로 사용하였다.
